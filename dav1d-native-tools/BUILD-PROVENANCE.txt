WHY THIS FILE EXISTS
--------------------------------------------------------------------------------
A binary in a package is anonymous. This file is how anyone later can tell which
native library came from which source, which toolchain and which build machine -
without which "rebuild it and see if it matches" is not a question that can even
be asked. Every time a binary is adopted into the package's runtimes/ tree, its
section here is updated from that build's output/<rid>/BUILD-INFO.txt.

HARDENING  (exploit-mitigation flags; added to every build script 2026-11-07)
================================================================================
The flags are pinned in linux/pins.env ("Security hardening flags"; Android
repeats them in android/pins.json) and every build passes them to meson as
c_args / c_link_args:

  Linux, Android : -fstack-protector-strong -D_FORTIFY_SOURCE=2
                   -Wl,-z,relro -Wl,-z,now
  Windows        : /GS /guard:cf  (compile)   /guard:cf  (link)
  macOS          : -fstack-protector-strong -D_FORTIFY_SOURCE=2

Every build is --buildtype=release (-O3), so _FORTIFY_SOURCE has the
optimisation it needs. Each gate now PROVES the flags landed, from the binary:
Linux - PT_GNU_RELRO, BIND_NOW, __stack_chk_fail and at least one __*_chk
import; Android - the same, with the __*_chk list reported (Bionic routes far
fewer calls through checked variants); Windows - the Control Flow Guard DLL
characteristic and a security cookie in the load configuration; macOS -
___stack_chk_fail imported, with the ___*_chk list reported.

WHAT THE TOOLCHAINS DID BY DEFAULT - measured 2026-11-07, before the flags
were added, on the then-shipped binaries and on the build images' compilers:

  linux-* (gcc 14.2.1 / 14.3.1, binutils 2.41, manylinux images)
                   no stack protector, no _FORTIFY_SOURCE defined, PARTIAL
                   RELRO only (GNU_RELRO present, no BIND_NOW). The shipped
                   binaries imported no __stack_chk_fail and no __*_chk.
  android-* (NDK 30.0.16248370 clang)
                   the driver passes -z relro -z now itself (shipped binaries
                   have GNU_RELRO + BIND_NOW), but no stack protector and no
                   _FORTIFY_SOURCE: no __stack_chk_fail, no __*_chk imports.
  osx-* (Apple clang, shipped 2026-08-29 binaries read with llvm-nm)
                   both already import ___stack_chk_fail (Apple clang's default
                   -fstack-protector, the weaker level); osx-arm64 also imports
                   ___memcpy_chk (the SDK enables FORTIFY for optimised builds).
  win-* (cl / clang-cl, shipped binaries read with llvm-readobj)
                   /GS was on (a SecurityCookie in the load configuration);
                   Control Flow Guard was OFF (no GUARD_CF DLL characteristic,
                   GuardCFFunctionCount 0).

WHICH SHIPPED BINARIES CARRY THE FLAGS
  linux-x64, linux-arm64, linux-riscv64
                 YES - rebuilt and adopted 2026-11-07 (entries below)
  android-arm64, android-x64
                 YES - rebuilt and adopted 2026-11-07 after device gates (entry
                 below; the older 2026-09-28 Android entry is the superseded build)
  win-x64, win-arm64, osx-arm64, osx-x64
                 NOT YET - their entries below are the earlier, unhardened
                 builds. Each is replaced, and this list updated, when it is
                 rebuilt with the current scripts.
